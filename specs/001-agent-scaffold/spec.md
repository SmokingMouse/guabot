# Feature Specification: Agent 脚手架（工具/Skills/MCP + IM 通道 + 简单记忆）

**Feature Branch**: `001-agent-scaffold`  
**Created**: 2026-02-25  
**Status**: Draft  
**Input**: User description: "实现一个基本的脚手架，需要具备下面几项功能：1）能使用工具 + Skills + MCP；2）能通过 Channel 和主流 IM 打通，模式 WaitingForMsg → AgentExec → SendMsg；3）具备简单的 Memory 管理机制，例如历史聊天 N 条。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 在主流 IM 中接入 Agent（Priority: P1）

一名业务使用者在公司常用的即时通信工具中，添加或配置一个“智能助手”入口，当发送
消息给该助手时，消息会通过脚手架转发给 Agent，并在收到 Agent 的回复后由脚手架再
发回到同一会话中，形成完整闭环，无需离开现有 IM 工具。

**Why this priority**: 这是整个脚手架的核心价值所在，如果不能在主流 IM 中完成一问一
答的闭环，其它能力（工具调用、记忆等）都无法真正被用户感知和使用。

**Independent Test**: 仅启用此用户故事相关配置（单一 IM 渠道、单一 Agent 实例），按
照预置测试账号发送简单问题（如“现在几点”或“介绍一下本机器人能力”），验证：
- 用户能在 IM 中看到助手欢迎语或简介；
- 用户发送消息后，在合理时间内收到来自助手的回复；
- 回复内容与问题相关，表明已经通过 Agent 正常处理。

**Acceptance Scenarios**:

1. **Given** 已正确配置一个 IM 渠道和 Agent 地址，用户在 IM 中向助手发送文本消息，
   **When** 脚手架收到该消息并转发给 Agent 后再将回复发回，**Then** 用户在同一会
   话中看到一条与其问题相关的回复消息。
2. **Given** IM 渠道配置信息缺失或错误，**When** 用户尝试向助手发送消息，**Then**
   系统在后台日志中记录清晰的错误原因，并且不会在 IM 中发送误导性的成功提示。

---

### User Story 2 - Agent 能调用工具 / Skills / MCP 扩展能力（Priority: P2）

一名技术运营人员希望为同一个 Agent 增加更多“能力插件”，例如：查询内部系统、调用
外部 API 或执行脚本。脚手架需要提供统一的能力接入机制，使 Agent 在处理用户消息时
可以选择并调用这些能力，并将结果回填到最终回复中。

**Why this priority**: 仅有基础问答的 Agent 价值有限，通过统一的工具/Skills/MCP 能力
接入，可以逐步扩展智能助手在 IM 场景中的应用深度和广度。

**Independent Test**: 在已有“IM 中接入 Agent”的基础上，仅增加一类简单的工具能力并
进行测试，例如“查询当前服务器时间”。验证：
- 在未配置工具时，Agent 只能给出泛化回答；
- 在配置工具后，Agent 回复中能够明显体现调用结果的变化（如返回具体时间或数据）。

**Acceptance Scenarios**:

1. **Given** 脚手架中已注册至少一个外部能力，并在 Agent 配置中启用，**When** 用户
   在 IM 中发出需要该能力才能回答的问题（如“帮我查一下当前运行环境的版本”），
   **Then** Agent 回复中包含通过该能力获取的具体信息，而不仅是泛化解释。
2. **Given** 某个已注册能力暂时不可用（例如超时或返回错误），**When** Agent 通过脚
   手架尝试调用该能力，**Then** 系统在日志中记录错误，并且向用户返回可理解的降级
   文本回复，而不是无响应或技术栈错误信息。

---

### User Story 3 - 保留最近 N 条对话作为上下文记忆（Priority: P3）

一名频繁与助手互动的用户希望在多轮对话中保持上下文连贯，例如可以先问“帮我想一个
项目名”，再说“用刚才那个项目名写一段介绍”，脚手架需要为每个会话维护最近 N 条
历史消息，并在调用 Agent 时一并提供，从而提升对话连续性。

**Why this priority**: 简单的记忆机制可以显著提升交互体验，而实现成本相对可控，适合
在首版脚手架中作为增强功能交付。

**Independent Test**: 仅在单一 IM 会话中启用记忆功能，预先配置 N 的默认值（例如 20
条）。通过一段多轮对话验证：
- Agent 在第二轮及以后的回复中能够参考前文信息；
- 当对话条数超过 N 时，最早的消息会被逐步丢弃，但最近几轮仍然有效。

**Acceptance Scenarios**:

1. **Given** 系统为每个会话维护最近 N 条消息，**When** 用户连续提出两到三个相关问
   题，**Then** Agent 的回复能够引用或准确理解前文内容（如“刚才我们说到的方案一”）。
2. **Given** 同一用户在不同会话中分别与助手对话，**When** 在新会话中发起问题，
   **Then** 该会话的记忆仅限于本会话的历史，而不会串联其它会话的数据。

---

### Edge Cases

- 当 IM 渠道出现网络波动或短暂不可用时，脚手架如何避免重复处理同一条消息？
- 当 Agent 回复超时或返回错误时，脚手架如何向用户解释并保证后续消息仍可继续处理？
- 当会话历史超过 N 条时，丢弃较早消息是否会影响关键业务信息的保留？
- [NEEDS CLARIFICATION: 记忆窗口 N 的默认值与最大值是多少，是否允许为不同渠道或
  会话类型配置不同的 N？]

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 在至少一种主流即时通信工具中，为用户提供一个可用的“智能助
  手”入口，使用户可以通过该入口发起对话并收到 Agent 的回复。
- **FR-002**: 系统 MUST 实现 WaitingForMsg → AgentExec → SendMsg 的基本处理链路，即
  能够从 IM 渠道拉取或接收消息，调用 Agent 完成处理，并将回复发送回同一会话。
- **FR-003**: 系统 MUST 提供统一的能力接入机制，使 Agent 能够在处理请求时调用已注
  册的工具 / Skills / MCP 能力，并将调用结果整合进最终回复中。
- **FR-004**: 系统 MUST 为每个会话维护一段有限长度的历史对话（最近 N 条消息），并
  在调用 Agent 时将这些历史一并传递，以支持多轮对话的上下文理解。
- **FR-005**: 系统 MUST 提供基础的配置能力，使运维或开发人员可以为不同环境配置 IM
  渠道、Agent 端点以及启用的工具 / Skills / MCP 集合。
- **FR-006**: 系统 SHOULD 允许按会话或渠道维度关闭记忆功能或调整记忆窗口大小，以兼
  顾隐私、安全或成本需求。
- **FR-007**: 系统 MUST 记录关键操作日志，包括消息收发、工具调用结果和异常信息，以
  便后续排查和审计。
- **FR-008**: 系统 MUST 在请求失败或能力调用异常时，向用户返回可理解的错误或降级提
  示，而不是暴露内部错误细节。

### Key Entities *(include if feature involves data)*

- **会话（Conversation）**: 表示在某个 IM 渠道中的一段连续对话，包含唯一会话标识、
  所属用户或群组标识、创建时间以及状态。
- **消息（Message）**: 属于某个会话的一条用户或 Agent 消息，包含发送方类型、时间
  戳、内容摘要以及是否已成功同步到 Agent 或 IM。
- **能力（Capability）**: 供 Agent 调用的外部能力抽象，如工具、Skill 或 MCP 端点，
  包含唯一标识、描述以及可用状态。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在至少一种目标 IM 渠道中，80% 以上的试用用户可以在首次配置后 5 分钟内
  完成“发送一条消息并收到 Agent 回复”的闭环体验。
- **SC-002**: 在正常网络条件下，从用户在 IM 中发送消息到收到 Agent 回复的端到端时
  间，90% 的请求不超过 5 秒。
- **SC-003**: 在开启记忆功能的会话中，至少 80% 的多轮对话用例中，用户认为 Agent
  回复“能记住前文”，以内部评估或问卷调研结果为准。
- **SC-004**: 在上线后首个观察周期内，与“IM 中 Agent 无响应/响应错误”相关的用户
  投诉或内部工单数量低于全部会话次数的 1%。

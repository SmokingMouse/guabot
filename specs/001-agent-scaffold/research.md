# Phase 0 Research: Agent 脚手架（工具/Skills/MCP + IM 通道 + 简单记忆）

**Feature**: `001-agent-scaffold`  
**Spec**: `specs/001-agent-scaffold/spec.md`  
**Plan**: `specs/001-agent-scaffold/plan.md`

## 决策 1：IM 渠道接入方式

- **Decision**: 首版采用 IM 平台提供的 HTTP 回调/Webhook 作为主要接入方式，必要时辅
  以轮询接口作为补充或容错方案。
- **Rationale**:
  - 回调/Webhook 模式可以减少轮询延迟与无效请求，更符合实时对话场景；
  - 大多数主流 IM（企业微信、飞书、Slack 等）均支持以 HTTP 回调方式推送消息；
  - 对于暂不支持回调的场景，可以通过独立的轮询任务适配，不影响主架构设计。
- **Alternatives considered**:
  - 纯轮询：实现简单，但在用户量增加后会带来较大无效流量与延迟；
  - 长连接推送（如 WebSocket）：部分 IM 不支持，且对运维环境有额外要求，首版暂不采
    用，将在后续演进中评估。

## 决策 2：记忆窗口 N 的策略

- **Decision**: 全局默认记忆窗口 N=20，单会话最大记忆窗口 200 条，允许按“IM 渠道”维
  度进行配置覆盖（例如内部测试环境可用更大窗口）。
- **Rationale**:
  - 默认 20 条足以覆盖大部分短会话的上下文需求；
  - 上限 200 条可以在需要时覆盖较长讨论，但不会无限制增长；
  - 按渠道配置可以根据不同 IM 的使用习惯与资源约束做微调（如机器人群 vs 私聊）。
- **Alternatives considered**:
  - 固定 N=20 且不允许修改：实现最简单，但难以适应不同业务环境；
  - 无上限或极大上限（如 1000+）：对内存和下游 LLM token 成本不友好，不符合极简与成
    本可控的原则。

## 决策 3：是否持久化会话与记忆

- **Decision**: 首版仅在内存中存储会话与最近 N 条消息，不做持久化；为未来持久化（如
  Redis/数据库）预留抽象接口与适配层。
- **Rationale**:
  - 当前目标以快速交付 MVP 为主，内存实现最简单、变更成本最低；
  - 规格中尚未提出强制审计/合规要求，短期内不需要长期保留聊天记录；
  - 通过在内部抽象中隔离存储实现，后续引入 Redis/数据库时不影响上层逻辑。
- **Alternatives considered**:
  - 立即采用 Redis：可支持多实例共享状态，但增加运维与复杂度，不符合首版极简目标；
  - 采用关系型数据库：适合强审计场景，但建模与运维成本更高，暂不需要。

## 决策 4：能力接入方式（工具 / Skills / MCP）

- **Decision**: 定义一层统一的 Capability 抽象，内部通过适配器分别对接“本地工具调用
  / 现有 Skills 接口 / MCP 协议”，对上层 Agent 暴露统一接口。
- **Rationale**:
  - 减少 Agent 侧的耦合，使其只关心“调用能力”而不是具体协议；
  - 方便后续引入新类型的能力（如内部 RPC、GraphQL 等），只需增加新的适配器；
  - 符合宪章中关于“清晰边界”和“渐进演化”的要求。
- **Alternatives considered**:
  - 在 Agent 内部直接分别对接三种能力：短期可行，但会使 Agent 逻辑膨胀且难以测试；
  - 将某一类能力（如 MCP）作为唯一方案：缺乏灵活性，且与部分已有能力体系整合成本高。

## 决策 5：日志与可观测性

- **Decision**: 使用结构化日志记录每一次 IM 消息收发与能力调用；预留统计指标（如调
  用次数、失败率、延迟）以便后续接入监控系统。
- **Rationale**:
  - 符合宪章“可观测性与运维”要求；
  - 便于排查“消息丢失/重复”“能力调用失败”等问题；
  - 前期可以先通过日志分析，后续再逐步接入指标系统。
- **Alternatives considered**:
  - 仅使用简单打印：不利于生产环境排查；
  - 一开始就接入完整的指标/追踪系统：实现与运维成本较高，不符合首版极简目标。

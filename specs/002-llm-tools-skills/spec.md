# Feature Specification: LLM 驱动决策与 Tools/Skills 联通验证

**Feature Branch**: `002-llm-tools-skills`  
**Created**: 2026-02-25  
**Status**: Draft  
**Input**: User description: "现在有了基本的脚手架，但是还没有大模型决策的部分，需要将这部分也引入。最终验证 LLM + Tools + Skills 流程是通的。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - LLM 在 IM 中自动决策是否调用工具（Priority: P1）

一名业务用户在主流 IM 中向智能助手发送一个问题，例如“查一下当前服务状态”。助手背后
的 LLM 会读取最近 N 条对话上下文，自动判断是否需要调用某个工具/Skill 获取数据，并在回
复中体现调用结果，而不是单纯给出泛化解释。

**Why this priority**: 没有大模型决策，脚手架只能做“固定路由 + demo 能力”，无法体现
LLM + Tools + Skills 的真正价值。让 LLM 主导“是否调用哪个工具”是这个迭代的核心目标。

**Independent Test**: 在现有脚手架分支基础上，启用一个真实的 LLM 端点和一两个简单工具
能力，通过 IM 发送多条问题，验证：

- 对单纯闲聊类问题，LLM 不调用工具，也能给出自然回复；
- 对需要外部数据的问题，LLM 会显式通过能力层调用工具，并把结果融合到回复中；
- 整个过程在日志/调试界面中可观测（能看到“LLM 决策 → 工具调用 → 回复”链路）。

**Acceptance Scenarios**:

1. **Given** 已配置好 LLM 端点和“当前时间”工具，用户在 IM 中发送“现在时间是多少？”，
   **When** LLM 判断需要调用工具并通过能力层发起调用，**Then** 回复中包含具体时间结
   果，而不是笼统的回答。  
2. **Given** 同一环境下，用户发送“讲个笑话”，**When** LLM 判断不需要调用工具，
   **Then** 回复为自然语言笑话，且日志中没有工具调用记录。

---

### User Story 2 - LLM 驱动多步 Tools/Skills 调用（Priority: P2）

一名运营或开发人员希望通过 IM 向助手发出稍复杂的请求，例如“帮我先查一下今天的错误数
量，再总结一个一句话报告给我”。LLM 需要能够在单轮对话中决策并执行多步工具/Skill 调
用，然后把多个调用结果整理成自然语言汇总给用户。

**Why this priority**: 单步工具调用只能验证基础链路，多步工具/Skill 调用可以验证 LLM
在“工具编排”和“结果整合”上的能力，是后续自动化工作流的基础。

**Independent Test**: 仅在内部测试环境中启用两种示例能力（如“查询错误计数”“查询当
前版本号”），通过 IM 发起一条复合指令，验证：

- LLM 至少发起两次不同能力调用；
- 回复中同时包含多个调用结果的汇总与简要结论；
- 如果其中一个调用失败，LLM 能够在回复中进行合理说明或降级，而不是直接报错。

**Acceptance Scenarios**:

1. **Given** 已注册“错误计数查询”和“版本信息查询”两个能力，**When** 用户在 IM 中
   发送“帮我查一下今天错误数和当前版本，并给个一句话总结”，**Then** 回复中包含两项
   信息以及一句汇总结论。  
2. **Given** 其中一个能力暂时不可用，**When** LLM 通过能力层尝试调用失败，**Then**
   回复中明确说明某部分信息暂缺，但仍提供其它可用信息，而不是完全失败。

---

### User Story 3 - 可观测的 LLM + Tools + Skills 调试视图（Priority: P3）

一名开发/运维同学希望能够在日志或调试工具中清晰地看到某一次对话的完整执行过程，以便
排查“LLM 为什么没有调用工具”或“为什么选了错误的工具”等问题。系统需要在不暴露敏感
内容的前提下，提供 LLM 决策与工具调用的关键轨迹。

**Why this priority**: LLM 决策往往不透明，如果没有可观测性，很难在生产环境中定位问题
和调优提示词/工具设计。

**Independent Test**: 在测试环境中开启调试日志或追踪，对一条复杂请求进行多次重放，验
证：

- 日志中能看到“收到用户消息 → LLM 决策（包含选中的工具名称）→ 工具调用参数 → 工
  具返回结果摘要 → 最终回复”的关键节点；
- 不会在日志中泄露敏感信息（如真实用户隐私字段）。

**Acceptance Scenarios**:

1. **Given** 系统开启标准日志级别，**When** 为某个会话 ID 收集一段时间内的日志，
   **Then** 能够根据会话 ID 复原每次 LLM 调用对应的工具调用记录和结果。  
2. **Given** 日志存储在内部受控环境，**When** 安全团队抽查日志，**Then** 未发现明
   文存储的敏感字段（如密码、身份证号等）。

---

### Edge Cases

- 当 LLM 返回的“工具调用意图”不匹配任何已注册能力时，如何安全地降级处理？
- 当 LLM 决策需要调用的工具数量非常多（例如超过预设上限）时，是否要做截断或批处理？
- 当工具响应时间过长或失败时，LLM 应如何在回复中表达不确定性而不是给出误导性结论？
- 当前版本仅支持单一 LLM 提供方，多 LLM 提供方以及按渠道/场景选择不同后端的能力将作
  为后续特性单独规划，不在本次范围内。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 在现有脚手架基础上，引入一个可配置的 LLM 决策层，使其能够根
  据用户消息和最近 N 条对话历史，判断是否以及如何调用工具/Skills。
- **FR-002**: 系统 MUST 通过统一的能力层（CapabilityRegistry 等）为 LLM 提供工具/Skill
  列表，并支持 LLM 在单次请求中调用一个或多个能力。
- **FR-003**: 系统 MUST 支持在同一对话中混合出现“纯 LLM 回复”（不调用工具）和“LLM
  + 工具结果融合”的回复，并在日志中标记实际执行路径。
- **FR-004**: 系统 MUST 对每次 LLM 请求及随后的工具调用记录必要的调试信息（例如选中
  的工具名称、调用耗时、成功/失败状态），以便后续排查问题。
- **FR-005**: 系统 SHOULD 提供基础的错误与超时处理策略，当工具不可用或超时时，LLM 能
  够获得足够信息，以便向用户返回合理的降级文案。
- **FR-006**: 系统 MUST 提供配置项控制可被 LLM 使用的工具集合（按环境/渠道），避免出
  现 LLM 访问未授权能力的情况。
- **FR-007**: 系统 MUST 在至少一个 IM 渠道上实现“真实 LLM + 至少 1 个工具/Skill”的
  端到端验证用例，并提供相应的手工验收步骤说明。

### Key Entities *(include if feature involves data)*

- **LLM 会话上下文（LLMContext）**: 表示 LLM 在执行某次决策时看到的输入，包括用户
  消息、最近 N 条历史、当前可用能力列表等。
- **工具调用计划（ToolPlan）**: 表示 LLM 决策出的工具调用意图，例如要调用哪些工具、
  顺序如何、需要哪些参数等（可以是结构化中间结果或提示词片段）。
- **执行轨迹（ExecutionTrace）**: 记录一次完整“LLM + Tools + Skills”执行过程的关键
  节点，包含时间戳、调用顺序、成功与否等摘要信息。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在测试环境中，针对“需要工具调用”的用例集，至少 80% 的请求中 LLM 能够
  成功触发正确的工具调用，并将结果融入回复（以人工评估为准）。
- **SC-002**: 在同一环境下，针对“纯对话/闲聊”用例集，至少 90% 的请求中 LLM 不会发
  起不必要的工具调用（以日志中工具调用次数统计为准）。
- **SC-003**: 对于包含 2 个及以上工具调用的复合请求，用例集中至少 70% 的请求能够完
  成所有预期的工具调用，并产出结构清晰的汇总回复。
- **SC-004**: 在一次端到端回归测试中，针对 LLM + Tools + Skills 场景的关键用例，每
  条用例的执行轨迹都可在日志或调试视图中被完整复原，不存在“黑盒无法解释”的关键步骤。

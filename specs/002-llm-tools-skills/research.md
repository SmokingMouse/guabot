# Research: LLM 驱动决策与 Tools/Skills 联通验证

**Branch**: `002-llm-tools-skills`  
**Date**: 2026-02-25  
**Spec**: [`spec.md`](./spec.md)  
**Plan**: [`plan.md`](./plan.md)

本文件汇总了围绕本特性相关技术与设计未知点的研究结论，采用“Decision / Rationale / Alternatives” 结构，作为后续设计与实现的依据。

## 1. LLM 接入方式与提供方

- **Decision**: 首版仅接入单一 LLM 提供方，并通过轻量 HTTP/SDK 客户端进行调用，不引入任何重型编排框架。
- **Rationale**: 
  - Guabot 宪章要求优先采用极简实现，避免 LangChain 等复杂抽象；
  - 本迭代的目标是验证 LLM + Tools + Skills 的端到端链路，而不是比对多家模型效果；
  - 单一提供方可以显著降低配置复杂度和故障面，有利于快速迭代；
  - 未来需要多提供方路由时，可以在现有决策层外包一层“LLMProviderRouter”，不影响当前设计。
- **Alternatives considered**:
  - 同时接入多家 LLM 提供方并按渠道/场景路由：灵活性更强，但会显著增加配置与测试成本，与当前验证目标不匹配；
  - 使用现成编排框架（如 LangChain）统一管理 LLM 与工具：会引入不必要的复杂依赖，与宪章极简主义原则冲突。

## 2. LLM 决策与工具编排模式

- **Decision**: 采用“LLM 生成工具调用意图 → 由本地编排层解析并执行”的模式，工具调用链路由本地代码掌控，而非让 LLM 直接注入任意代码或命令。
- **Rationale**:
  - 可以在本地对 LLM 生成的意图进行校验（如工具是否在允许列表、参数是否合法），增强安全性；
  - 保留对执行顺序、重试策略和错误处理的精细控制，便于满足可观测性与回放需求；
  - 与现有 `capabilities` 设计契合，复用统一的能力注册与调用入口。
- **Alternatives considered**:
  - 允许 LLM 直接返回“要执行的 shell/SQL/HTTP 请求”：灵活但安全风险极高，不符合当前项目定位；
  - 完全由本地规则决定工具调用，LLM 仅做自然语言回复：无法体现“LLM 主导决策”的目标，也无法覆盖 P2 用户故事中的多步编排场景。

## 3. 会话上下文与历史条数 N 的控制

- **Decision**: 为 LLM 提供“当前用户消息 + 最近若干条历史（例如 5～10 条）+ 当前可用工具/Skills 列表”的上下文，具体 N 值通过配置项控制，默认采用较小值以控制 token 成本。
- **Rationale**:
  - 多轮对话场景下，LLM 需要了解最近几轮上下文才能正确判断是否调用工具，但无需加载远古历史；
  - 将 N 配置化便于在不同环境（开发/测试/生产）下权衡效果与成本；
  - 现有 IM Webhook 侧已能获取完整会话 ID 和消息序列，增加一个“截断最近 N 条”的逻辑成本较低。
- **Alternatives considered**:
  - 始终提供全量历史：在长会话下 token 成本过高，且对决策收益有限；
  - 只提供当前消息：会影响某些依赖前文语境的决策质量，例如“再查一次刚才那个服务状态”。

## 4. 工具/Skills 暴露方式与安全边界

- **Decision**: 仅通过受控列表向 LLM 暴露工具/Skills，并在提示词或轻量 schema 中描述各能力的用途和输入输出约束；实际调用时由本地能力层进行参数校验与执行。
- **Rationale**:
  - 可以明确控制哪些能力对 LLM 可见，避免访问未授权或高风险操作；
  - 通过简洁描述文档有助于提高 LLM 选择合适工具的成功率；
  - 保持与现有 `CapabilityRegistry` 之类结构的一致性，便于扩展与调试。
- **Alternatives considered**:
  - 将所有内部 API 直接暴露给 LLM：难以控制边界和权限，引入安全风险；
  - 只暴露单一工具：无法覆盖多步编排与结果整合的需求，不满足 P2 用户故事。

## 5. 可观测性与执行轨迹格式

- **Decision**: 为每次 LLM + Tools/Skills 调用生成结构化执行轨迹（ExecutionTrace），包含会话 ID、LLM 请求摘要、所选工具/Skills 名称、调用结果摘要、耗时与状态，并写入结构化日志；调试视图在此基础上进行渲染。
- **Rationale**:
  - 满足宪章中对“结构化日志 + 可追踪关键节点”的要求，便于问题排查和效果评估；
  - ExecutionTrace 作为领域概念已在 `spec.md` 中定义，天然适合作为日志/调试视图的核心数据模型；
  - 在初期阶段，结构化日志即可支撑大部分调试场景，无需引入额外追踪系统。
- **Alternatives considered**:
  - 仅在控制台打印人类可读日志：短期可用但不利于程序化分析与过滤；
  - 立刻接入完整分布式追踪系统：超出当前迭代范围，增加运维复杂度。

## 6. 测试策略与验证范围

- **Decision**: 在测试环境中针对代表性用例集（纯闲聊、单步工具调用、多步工具编排）进行端到端验证，重点通过日志与人工评估验证 LLM 决策的正确性与工具调用链路；自动化测试侧重于“决策层输出是否符合约束”“能力层调用是否按预期执行”，而非评估语言质量。
- **Rationale**:
  - LLM 回复的自然语言质量难以完全自动化测试，适合作为人工评估部分；
  - 决策层与工具调用层的行为则相对结构化，更适合作为自动化测试的重点；
  - 该策略在保证质量的前提下，控制了测试实现成本。
- **Alternatives considered**:
  - 只做端到端人工验证：长期回归成本过高，不符合“可验证行为与测试优先”的原则；
  - 大量引入基于 embedding 的自动打分：实现复杂且与当前验证目标不完全匹配。

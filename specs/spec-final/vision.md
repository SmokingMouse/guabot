## 架构总览

```
┌──────────────────────────────────────────────────────────┐
│                     Guardrails Layer                     │
│   可配置规则（审批、频率限制、自主权限）——agent 不可绕过   │
└──────────────────────────────────────────────────────────┘
                            ↕
┌──────────────────────────────────────────────────────────┐
│                      Session Layer                       │
│                                                          │
│  ┌──────────────────┐    ┌───────────────────────────┐   │
│  │  对话 Session    │    │    自规划 Session          │   │
│  │  用户发起        │    │    agent 发起              │   │
│  │  reactive        │    │    proactive + 调度器      │   │
│  └──────────────────┘    └───────────────────────────┘   │
│                                                          │
│  每个 Session 包含：                                      │
│    participants（用户 / agent / 数据源）                  │
│    goal + metrics + deviation_threshold                  │
│    plan（任务树，动态更新）                               │
│    reflection（反思记录）                                 │
│                                                          │
│  Session 内通信：Message Bus（所有参与者平等）            │
└──────────────────────────────────────────────────────────┘
                            ↕
┌──────────────────────────────────────────────────────────┐
│                   3-Layer Memory                         │
│  Layer 1  流水层   原始 session 记录，永久保留            │
│  Layer 2  事件层   跨 session 提炼的结构化事件            │
│  Layer 3  画像层   跨 session 糅合的稳定抽象，注入 prompt │
└──────────────────────────────────────────────────────────┘
                            ↕
┌──────────────────────────────────────────────────────────┐
│                    Skill System                          │
│  获取顺序：本地 → 外部 registry → 自写                   │
│  激活流程：可配置 review（自动测试 / 人工确认）           │
└──────────────────────────────────────────────────────────┘
```

## 自规划 Session 执行循环

```
用户设定高层目标
    ↓
agent 推断成功指标草稿 → 用户确认
    ↓
agent 自主分解任务树（plan）
    ↓
┌─────────────────────────────────┐
│  Execute（调用 skills / tools） │
│       ↓                         │
│  Observe（指标采集，偏离检测）  │  ← 循环
│       ↓                         │
│  Reflect（触发时：归因 + 报告） │
│       ↓                         │
│  Replan（更新任务树 / 指标）    │
└─────────────────────────────────┘
    ↓
目标达成 / 用户终止
```

## 反思触发机制

| 触发类型 | 场景 | 优先级 |
|----------|------|--------|
| 问题驱动 | 指标偏离超过阈值（实际 < 预期 × 0.5） | 核心/初心 |
| 缺口驱动 | 检测到缺少 skill 或机制 | 核心 |
| 用户触发 | 用户主动要求反思 | 高 |
| 定时触发 | 每天设定时间例行反思 | 兜底 |

反思工作流：收集上下文 → LLM 归因（必要时问用户）→ 生成报告 → 更新 plan / 触发新 goal

## 部署形态

- 持续运行的本地服务器（daemon），关闭关机权限
- 调度器内置，支持：cron 定时 / 事件驱动 / agent 自主写入调度意图
- 多 goal 并发：每个 goal 对应一个自规划 session，并行运行

## 一句话目标

guabot 是一个运行在本地的自主代理，能够接受高层目标，自主分解任务、执行、反思、改进，
并在此过程中不断扩展自身能力（skills），最终实现对复杂长期目标的全流程自动化。

## 核心能力矩阵（已达成共识）

| 能力 | 描述 |
|------|------|
| 目标分解 | 接受高层目标（如"运营小红书账号实现吸粉"），自主拆解为任务树 |
| 自主执行循环 | Execute → Observe → Reflect → Replan，持续推进目标 |
| 反思驱动改进 | 识别"人的问题"（需学习新技能）和"事的问题"（需换策略） |
| Skill 获取/创建 | 发现技能缺口后，引导 guabot 探索或自己编写新 skill |
| 外部数据订阅 | 异步 pipeline 接入外部数据（如小红书数据），guabot 订阅消费 |

## 典型场景：小红书账号运营

**用户输入的目标**：运营小红书账号，实现吸粉增长。

**guabot 自主分解的任务树（示例）**：

```
Goal: 小红书账号增长
├── 内容策略
│   ├── 分析同类账号（竞品对比）
│   ├── 确定内容方向和风格
│   └── 制定发帖节奏（频率、时间）
├── 内容生产
│   ├── 选题生成
│   ├── 文案撰写
│   └── 发布（skill: xiaohongshu.post）
├── 数据分析
│   ├── 订阅帖子数据（浏览、点赞、收藏、评论）
│   ├── 识别高/低表现内容
│   └── 归因分析
└── 反思与调整
    ├── 内容反思（这类选题为什么没人看？）
    ├── 策略调整（换赛道？换风格？）
    └── 技能补充（需要学习 SEO？需要图片处理 skill？）
```

**数据获取层**（分阶段，按可行性降级）：
1. 直接 API（如有）
2. 浏览器自动化（Playwright/Selenium skill）
3. 异步数据抓取 pipeline → guabot 订阅

## 开放问题（讨论中）

### Q1: 人工介入的边界 ✅

**结论**：可配置规则模版，类比物理定律——agent 必须遵守，不可绕过。

规则示例：
```yaml
guardrails:
  require_approval:
    - action: post          # 发帖需确认
    - action: delete        # 删除需确认
  auto_allowed:
    - action: draft         # 草稿自动生成
    - action: analyze       # 数据分析自动执行
  rate_limits:
    - action: post
      max_per_day: 3
```

Agent 在执行前检查 guardrails，命中 require_approval 则暂停并通知用户。

---

### Q2: 目标状态的持久化 ✅

**结论**：Goal 不是独立层，它是 Session 的属性。Session 是最小单元。

**Session 结构**：
```
Session
├── participants   # 参与者（用户、agent、其他 agent）
├── context        # 对话历史 / 执行上下文
├── goal           # 本 session 要达成的目标
├── reflection     # 本 session 的反思记录
└── profiles       # 参与者的局部画像（session 内抽象）
```

**两种 Session 类型**：
- 对话 session：用户发起，reactive，有来有往
- 自规划 session：agent 发起，proactive，自主循环执行目标

两者共享同一个 Session 抽象，自规划 session 额外有调度机制和目标文件。

**3层记忆 = 跨 session 的知识层**：
- Layer 1（流水）= 各 session 的原始记录
- Layer 2（事件）= 跨 session 提炼的事件
- Layer 3（画像）= 跨 session 糅合的稳定抽象

**跨 session 信息共享**：
同一个用户在 session A 和 session B 里的画像，由 Layer 3 负责糅合。
这解决了"同一个人在不同 session 里的抽象可以合并"的问题。

**多 goal 并发**：可以同时有多个活跃 goal，每个对应一个自规划 session。
例如：小红书运营 session + 辅助学数学 session 并行运行。

---

### Q3: Skill 获取与自写的安全边界 ✅

**结论**：有序执行 + 可配置 review 规则（同 Q1 guardrails 体系）。

执行顺序：
1. 搜索本地已有 skills
2. 搜索外部 skill 源（类似 npm registry）
3. 自己编写新 skill
4. Review（可配置：自动测试 / 人工确认 / 两者）
5. 激活使用

**调度**：在自规划 session 内，guabot 自己调度自己；
也可以被 session 内其他参与者（用户或其他 agent）控制。

Review 规则纳入统一的 guardrails 配置体系（同 Q1）。

### Q4: 自规划 session 的唤醒机制 ✅

**结论**：都有，可配置。

- 定时器（cron-like，如"每天 9 点推进小红书 session"）
- 事件驱动（新数据到达 → 触发分析）
- agent 自主调度（反思时写入"明天要发帖" → 到时间自唤醒）

统一纳入 guardrails 配置体系。

---

### Q5: Session 内的参与者模型 ✅

**结论**：开放参与者模型，支持多类型。

- 用户：随时可介入干预
- 多 agent：支持（如批评者 agent + 执行者 agent 协作）
- 外部数据源：可作为参与者（如小红书数据 pipeline）

Session 的 participants 字段是可扩展的角色列表。

---

### Q6: Agent 自主创建新 Goal ✅

**结论**：可以，但受 guardrails 控制。

例如：小红书 session 反思发现"需要学 SEO" → guabot 可自主创建"学习 SEO" session。
但此类行为需在 guardrails 中明确授权（默认需用户确认，可配置为自动）。

## 讨论记录

### 2026-02-27 第一轮

**用户目标陈述**：
guabot 成为强大的本地代理，综合 skills 和本地资源解决复杂问题。
核心机制：反思 → 沉淀 → 工作 → 反思 的循环。
不要求一口气完成，而是小任务 + 拆解的形式。

**Q: 谁来做任务拆解？**
A: agent 自己拆。目标是高层的（如"账号增长"），agent 自主组织子任务。

**Q: 数据获取层的预期？**
A: 阶段性解决。优先直接 API，其次浏览器模拟，再次异步抓取 pipeline + 订阅。

**Q: 反思的输出是什么？**
A: 三类：
1. 自我改进（"我需要学 X 技能"，"我需要更果断"）
2. 策略调整（"这件事应该换做法"，更新任务计划）
3. Skill 缺口（引导 guabot 探索或自己编写新 skill）

### 2026-02-27 第二轮

**Q1: 人工介入边界** → 可配置 guardrails 规则模版
**Q2: 目标持久化** → Session 是最小单元，Goal 是 session 属性，3层记忆是跨 session 知识层
**Q3: Skill 自写安全** → 有序（搜索→外部→自写）+ 可配置 review，纳入 guardrails

### Q7: 本地 vs 持续在线 ✅

**结论**：guabot 运行在持续在线的服务器上，关闭关机权限。

这意味着：
- 自规划 session 的调度器可以可靠地按时唤醒
- 不需要云端调度层（当前阶段）
- 部署形态是一个长期运行的本地服务，而非桌面应用

---

### Q8: 反思的触发时机 ✅

**结论**：多种触发，但初心是"问题驱动"。

| 触发类型 | 场景 | 优先级 |
|----------|------|--------|
| 问题驱动 | 目标偏离（发帖效果差）、脱离掌控 | 核心/初心 |
| 缺口驱动 | 检测到缺少某个 skill 或机制 | 核心 |
| 用户触发 | 用户主动要求反思 | 高 |
| 定时触发 | 每天设定时间的例行反思 | 常规 |

**设计原则**：反思不是例行公事，而是对"事情不对劲"的响应。
定时反思是兜底，问题驱动才是初心。

### Q9: 成功标准如何定义 ✅

**结论**：agent 先推断草稿，用户确认后生效。

流程：
1. 用户创建 goal（"帮我运营小红书"）
2. agent 根据上下文 + 行业常识生成初始指标草稿
3. 用户确认或修改
4. 生效后写入 session goal，作为反思触发的基准

**指标结构示例**：
```yaml
goal: 小红书账号增长
metrics:
  - name: 粉丝增长
    target: +1000 / 3个月
    check_interval: 每周
  - name: 帖子平均点赞
    target: "> 50"
    check_interval: 每篇发布后 48h
  - name: 发帖频率
    target: 3篇/周
    check_interval: 每周
deviation_threshold: 实际值 < 预期值 * 0.5  # 触发反思
```

**动态调整**：指标不是一成不变的，反思后可以更新（如发现某类内容表现好，调整目标方向）。

### Q10: 反思 agent 工作流 ✅

**结论**：归因阶段可与用户交互，不闷头分析。

```
触发信号（偏离 / 缺口 / 用户 / 定时）
    ↓
收集上下文（近期执行记录、当前指标、历史反思）
    ↓
LLM 初步归因 → 必要时向用户提问（"你觉得问题出在哪？"）
    ↓
生成反思报告（结论 + 建议行动）
    ↓
输出到三处：
  ├── session.reflection（本 session 反思记录）
  ├── 更新 plan（调整任务树 / 指标）
  └── 可能触发：新 skill 搜索 / 新 goal 创建
```

---

### Q11: 多 agent 协作的通信机制 ✅

**结论**：消息总线（Message Bus）模式。

```
Message Bus
├── Executor Agent   （订阅任务消息，发布执行结果）
├── Critic Agent     （订阅内容消息，发布评分/建议）
└── Reflection Agent （订阅所有消息，发布反思报告）
```

所有 agent 平等，通过共享消息队列通信。
任何 agent 都可以发布消息、订阅感兴趣的消息类型。
用户也是消息总线上的一个参与者，可随时介入。
